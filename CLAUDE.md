## Testing

Two suites, two runners:

- **Vitest** (`bun run test`) — unit tests under `src/`, plus the static guards in
  `e2e/__guards__/`. Runs in CI on every push.
- **Playwright** (`e2e/specs/`) — full-stack e2e against a live localnet (Hardhat + contracts +
  mock oracle + graph-node + IPFS). **Not run in CI at all** — a local run is the only place the
  full stack is exercised.

**Before writing, moving, or debugging any e2e spec, read
[`docs/E2E-ISOLATION-MODEL.md`](docs/E2E-ISOLATION-MODEL.md).** It is short, and it exists
because the isolation rules are not guessable: `evm_revert` permanently wedges graph-node and
freezes the subgraph, so a snapshot in one spec silently breaks _other_ spec files in a way that
looks like flakiness.

**Do not run `bunx playwright test` over the whole suite for a verdict** — use the supported
protocol, which must be started inside tmux (the runner refuses otherwise):

```bash
cd ../sense-ai-e2e && tmux new-session -s e2e 'bash scripts/run-e2e-sharded.sh'
```

**Testnet mode** runs the same specs against the real Base Sepolia stack through the chain
adapter (`e2e/helpers/chain.ts`): seed-derived accounts funded by a treasury, Node-side signing,
no dev-node RPC methods. It is driven only by `sense-ai-e2e/scripts/testnet/run-e2e-testnet.sh`
(real model calls, real test gas). What runs and what is excluded, with reasons, is in
`e2e/CAPABILITIES.md` under "Testnet mode". Specs gate on `LIVE_STACK` from the adapter, never on
`process.env.E2E_LOCAL_SERVICES` (the `live-stack-gate` guard enforces this).

A single `playwright test` invocation reproduces the wedge described above. The tmux
requirement is because the run takes ~70 minutes and owns the ports, chain and Docker stack
throughout — if the caller dies (closed terminal, dropped SSH, an agent harness reaping its
child) the run dies partway and leaves the stack up. Detach with `Ctrl-b d`; it keeps running.

## Architecture

### Provider Stack (`src/main.jsx`)

Providers wrap the app in this order (innermost first in terms of dependency):
`BrowserRouter` → `ThirdwebProvider` → Redux `Provider` → `QueryClientProvider` → `PostHogProvider` → `ThemeProvider` → `SessionProvider`

### Route Structure (`src/pages/App.jsx`)

Public routes: `/auth`, `/error`, `/privacy-policy`, `/terms-and-conditions`, `/website-disclaimer`

Protected routes (require wallet + session): `/` → `UsageDashboard`, `/chat` → `Chat`, `/history` → `History`

All feature pages are lazy-loaded. App waits for Firebase and Thirdweb to initialize before rendering (shows `SplashScreen` until `appStatus === 'ready'`).

### Auth & Session Flow

1. Thirdweb manages wallet connection (supports in-app wallets and external wallets like MetaMask).
2. `SessionProvider` (`src/features/auth/SessionProvider.jsx`) derives a `sessionKey` (Web Crypto `CryptoKey`) by asking the user to sign a fixed message, then passing the signature through `deriveKeyFromEntropy` (`src/lib/crypto.js`). The key is held in React state — never persisted.
3. `useSession()` provides `{ sessionKey, status, ownerAddress, activeWallet }` throughout the app. Status values: `disconnected | deriving | ready | rejected | error`.

### Data Layer

All conversation and message data is encrypted client-side with the user's `sessionKey` using AES-GCM before being stored in **IndexedDB** (via Dexie, `src/lib/db.ts`). The DB schema has four tables: `conversations`, `messageCache`, `searchIndex` and `userMetadata` (the sync cursor).

There is one database per agent contract, named `SenseAI:<chainId>:<agent address>` by `src/lib/localStoreName.ts`. Conversation ids are counted by the agent, so a newly deployed agent starts again at 1; in a shared database a returning wallet would see the two agents' conversations merged and the old sync cursor would hide the new history. A missing or malformed chain id or agent address throws instead of naming a shared store, and `vite.config.ts` runs the same rule (`assertLocalStoreConfig`, which calls the function the browser calls) so a build or dev server stops with the reason rather than shipping a blank page; the reason says what was expected and describes the refused value by its shape only (empty, length, `0x` prefix, all hex), so a key pasted into the wrong setting is never printed (Vitest has its own configuration and does not run it; and when a running dev server is restarted by an edited settings file that fails the check, Vite prints the reason and keeps serving the old settings): the store module is in the first bundle, ahead of Sentry and the error boundary. A localnet build or a unit-test run with no agent address (the browser tests that run against no contracts; a test that loads the module unmocked) uses `SenseAI:localnet:unconfigured`. The `e2e/__guards__/local-store-per-agent` guard allows the Dexie library to be loaded only in `src/lib/db.ts` (type imports aside), one database there named from the build's chain id and agent address by `resolveLocalStoreName` imported from `localStoreName` (a local function of that name fails it), and requires the check in `vite.config.ts`. The `e2e/__guards__/build-config-checks` test runs the real Vite configuration, so a check still written there but no longer reached fails too. A localnet redeploy puts the agent at the same address, so after a chain reset clear the site data in a browser that was used before it. A database from before this naming (`SenseAI`) is neither read nor deleted; the wallet's history is synced again from the subgraph.

**`src/lib/dataService.ts`** — all IndexedDB read/write operations. Functions encrypt/decrypt on every access.

**`src/lib/messageCacheStore.ts`** — `writeMessageCache`, the only writer of the `messageCache` table. A prompt being sent, a sync, a branch rebuilding its history and a cancel all change the same stored list; each passes a merge function, and the write happens only if the row is still the one the merge was given (checked and put inside one IndexedDB transaction, merged again otherwise). Encryption stays outside the transaction, because IndexedDB commits a transaction left waiting on Web Crypto. Nothing is evicted: the local store is a full copy of what has been synced. Stored data that cannot be read is left alone unless the writer passes `replaceUnreadable` (the sync, a send, a new branch), so the sync still sees the conversation as unfinished and restores it. The `e2e/__guards__/message-cache-single-writer` guard lists the uses of the table allowed elsewhere (`get`, `where(...).toArray()`, `delete`) and fails on any other mention of it.

**`src/features/chat/promptParent.ts`** — whether a prompt can be sent and what it threads off (`composerStateFor`: `ready`, `loading` or `hold`). A branch's prompt is never flagged as a new conversation, and a branch that shows no messages is held: its history is not on this device, and a prompt sent then would lose the branch's origin. While held, `useHeldBranchRefresh` re-reads the branch's messages every 15 s and asks for a sync every 60 s. The wait lasts from `hold` until `ready` and is not ended by the `loading` each re-read passes through; ending it there would restart both timers every 15 s, and the longer one would never fire. Opening another conversation ends it (the state is kept per conversation), and nothing is asked for while the page is hidden.

**`src/lib/payloadStorage.ts`** — the only module that fetches payload bytes by CID. Source order for Autonomys ids is the per-network GCS mirror (`VITE_PAYLOAD_MIRROR_URL`, written through by the oracle at upload time) and then the Autonomys gateway; legacy Arweave ids go to the Irys gateway only; 404 skips to the next source, 5xx/429/network errors retry with the shared jittered backoff, and callers get a typed `not-found | unavailable | unsupported-cid` result. `syncWithRemote` returns `{ unavailablePayloads, graphUnavailable }`, holds the sync cursor while anything was unavailable (so The Graph re-serves it next pass) and `useConversations` turns the count into the `storageDegraded` UI flag behind `StorageUnavailableBanner` (a pass that failed before its payloads were read, at The Graph for one, gives no count and leaves the flag, and a dismissal of it, as they were). A pass fetches at most `PAYLOAD_FETCH_CONCURRENCY` (8) payloads at once (`src/lib/limitConcurrency.ts`, one pool per pass; results keep their order and every rule above), so a first sync of a large wallet does not send a gateway a burst it answers with 429. The `e2e/__guards__/no-raw-storage-gateways` guard forbids the gateway host names anywhere else in `src/`.

**`src/lib/graph/userUpdates.ts`** — what a sync reads from The Graph: every conversation updated since the cursor, in pages of 100 by keyset on `lastMessageCreatedAt` (newest first, each page from the last row's time inclusive, rows already read dropped by id, `skip` only inside a run of one time that fills whole pages; `src/lib/graph/keysetPages.ts`), and each conversation's messages and unanswered prompt requests with `first: 1000`, read on from their own query when that comes back full. Any failed request, an answer without its list, a full page with nothing new (`no-progress`), or a list still coming back in full pages after `MAX_KEYSET_PAGES` (1000 pages: 100,000 conversations, or 1,000,000 messages or prompt requests in one conversation, which no real wallet reaches; `too-many-pages`, so an endpoint serving new rows without end cannot keep a pass running for ever) throws `GraphFetchFailed` (list, reason and the error's name only; never the URL or variables): the sync then stores nothing from the pass and holds its cursor, which is set once, after the last page is stored, to the newest conversation read (milliseconds; the next pass asks from that second, rounded down, inclusive); a pass that reads no conversation leaves it where it was (never moved to the device's clock, which can run ahead of block time and would hide a new wallet's first conversation). A build with no Graph endpoint throws the same (`not-configured`). Such a failure is reported to Sentry once per page load per list and reason (`src/lib/graph/graphSyncReport.ts`; tags `check: graph-sync`, `list` and `reason`, and the error's name as `extra.errorName`; never its message), and the result's `graphUnavailable` becomes the `graphUnavailable` UI flag (a pass that fails before The Graph has answered leaves it undefined, and the flag as it was): the same banner then says the history could not be refreshed just now and will be tried again (each notice dismissed on its own, re-armed by a pass that succeeds), and a branch held for its history says so in its composer notice whether or not the banner was dismissed. The Graph documents 1000 as the largest `first` and no limit on a whole answer (graph-node's result-size, complexity and time limits are off unless set; the gateway's are not published); the largest page this asks for (100 conversations, 1000 of each nested list) has not been measured on the deployed endpoint. Inside a `skip` run, a row of the run updated mid-run can shift one row out of reach (see `keysetPages.ts`); it needs a page of conversations in one block second.

**TanStack Query** (`@tanstack/react-query`) manages server/blockchain state. The conversations key includes `sessionKey` for per-wallet data isolation: `['conversations', sessionKey, ownerAddress]`. The **messages** key does NOT include `sessionKey` — it is `['messages', conversationId, ownerAddress]` (see `Chat.tsx` / `useLiveResponse.ts`). Any code invalidating the messages query MUST use this exact key; adding `sessionKey` makes the invalidation a silent no-op (which previously stranded cancelled-prompt placeholders).

**`src/hooks/useLiveResponse.ts`** — the real-time update mechanism. It does NOT watch contract logs: on Base's public RPC that is one `eth_getLogs` per event per block (the #77 429 storm) and mainnet.base.org refuses `eth_getLogs` outright. Instead `src/hooks/liveStateProbe.ts` polls two `eth_call`s once per block (`pendingEscrowCount(user)`, `spendingLimits(user)`) batched into one request, and a change drives the retry/backoff sync queue that invalidates TanStack Query caches. Backoff on 429, pause while hidden. The `e2e/__guards__/no-log-watchers` guard forbids reintroducing `useContractEvents`.

### PWA Updates

The service worker is registered in `prompt` mode (`vite.config.ts`), never the self-reloading mode — the `e2e/__guards__/pwa-prompt-mode` guard pins this. `src/components/UpdatePrompt.tsx` (mounted next to the `Toaster` in `main.tsx`) turns a waiting worker into a "new version" toast whose Reload action calls `updateServiceWorker(true)`. The toast is deferred, or withdrawn, while `useIsMutating() > 0` or the session status is `deriving`, so a reload can never abort a wallet signature. `src/lib/staleChunkReload.ts` is the separate crash-recovery path for a lazy chunk that 404s after a deploy. Under vitest the virtual register module resolves to `src/test/pwaRegisterStub.ts`.

### Blockchain Interaction Pattern

All write operations go through `src/hooks/useChatMutations.tsx`. Every mutation:

1. Symmetrically encrypts the payload with the user's `sessionKey`.
2. Asymmetrically encrypts the session key for the TEE oracle using `VITE_ORACLE_PUBLIC_KEY`.
3. Calls a contract method on `EVMAIAgentEscrow` via Thirdweb (`sendAndConfirmTransaction`).
4. Parses the transaction receipt logs to extract on-chain IDs returned by the contract.

**One paid send at a time (`src/features/chat/useOneSendAtATime.ts`)** — the chat takes its mutations through this hook, never from `useChatMutations()` directly. The three that send a paid prompt (a prompt or a resent edit, regenerate, branch) carry a mutation key starting `'paid-send'`, and their `mutate` does nothing while a send is under way; `mutateAsync` is not offered. A send is under way from the moment it starts (read from the query client's mutation cache, so a second press in the same moment is refused and the lock is still there when the chat is left and opened again) until the chat's own `onSuccess` has finished writing the prompt to the local store, since only then is the composer cleared and the answer shown as awaited. That write is counted per query client, so a chat opened again while it runs still refuses. The library runs the chat's `onSuccess` only in the chat that started the send: if the chat is left before the transaction is confirmed, the chat's own save and the warning below do not run, and the prompt comes back through the sync. `isSending` is true for the same span, and the edit box and an answer's actions are off with the reason in `src/components/ai/sendingReason.ts`. Cancel and refund are not part of it. When that work fails after the send was confirmed (the local save or its encryption, or a save handler with no wallet address, which throws rather than returning), or has not settled after `SAVE_GIVE_UP_MS` (30 s; a save blocked by another tab would otherwise hold the lock for the page load), the hook does what a call site could forget: it warns that the prompt (or the new answer asked for, or the branch) was sent and paid for and when it will appear: "once your history syncs" for a prompt in a conversation or an edit, "when the answer arrives" for a new conversation or a regenerate, "in your history once it is listed" for a branch (it has no answer to wait for), "unless saving on this device keeps failing" in every case (one toast id, shown until closed, a second failure replaces it); holds the send (`src/features/chat/unsavedSends.ts`, below); calls the caller's `onSaveFailed` with the receipt's ids and the time the send was confirmed (the chat clears the composer, or closes the edit box, so the paid text is not sent again by reflex; the composer then shows the prompt from those ids in memory at that time, awaiting its answer, in its conversation or the new one it started, and opens the cancel window from that time, so the refund countdown and the window run from the confirmation, with no extra chain read); asks for a sync by invalidating `['conversations', sessionKey, ownerAddress]` for the session the send was started in and re-reads `['messages', conversationId, ownerAddress]` for the conversation it shows in; and reports to Sentry once per page load (tags `check: paid-send-save` and `send: <kind>`). The chat's `onSaveFailed` and its `onSuccess` after the save act only while the conversation the send was made in (none, for the new chat) is still the one open, read from the store at that moment (`isActiveConversation` in `src/features/chat/unsavedPrompt.ts`, via `useAppStore`): otherwise nothing is shown in the open conversation, nothing navigates, and its draft and any open edit box are left alone; the hold is registered for the right conversation all the same. A save that finishes after it was given up on adds nothing twice (`appendLiveMessages` skips ids already shown), and when the composer holds text other than the sent prompt by then (typed since the composer was freed; an empty or blank composer is not a draft) it neither clears it nor moves to the new conversation the send started. The held send is kept per query client, as the lock's count is, and saved in `localStorage` per wallet and agent store (`src/features/chat/unsavedSendsStorage.ts`, keyed by `resolveLocalStoreName`: ids, kind, conversation keys and the confirmation time only, never a prompt's text or any message content; every access wrapped, so storage that throws leaves it in memory only; a saved value is rebuilt field by field and anything else is ignored, and what is written is picked field by field too, nested places included), so a reload restores it. Each write first reads the saved list again and merges it with this tab's holds (one per send), so a hold another open tab saved is kept and one it ended (still in force, last seen saved, gone now) is not brought back, and the window's `storage` event takes another tab's change in, so a hold made in one tab holds in the other and one ended there ends here; storage that cannot be read changes nothing. The prompt shown from its receipt is kept with the hold in memory only (`shownPrompt`, `attachShownPrompt`) and shown again, with its cancel control, when its conversation is opened again, until the hold ends. While it lasts the composer of its conversation (and, for a new conversation, the new-chat composer too) cannot send and says why (`ComposerHoldNotices`; `UNSAVED_SEND_COMPOSER_REASON` in the conversation, `UNSAVED_NEW_CONVERSATION_REASON` in the new chat, which never says "here"), edit on a prompt and the edit box's save in that conversation are off with `UNSAVED_EDIT_REASON` (saving an edit sends a paid prompt; edit is `aria-disabled` through `SwitchedOffButton`, the save is disabled with the reason as its description, as for a send under way), and regenerate and the branch menu on the affected answer (the one a prompt threaded off, the one regenerated, the one branched from) are off with `UNSAVED_SEND_REASON`, or `UNSAVED_BRANCH_REASON` for a branch (`useUnsavedSendHold`; all in `src/components/ai/sendingReason.ts`, and each says when it ends: once the prompt is back in the history, or the branch is listed, or at the latest an hour after it was sent, when a refund can be claimed for a prompt); a branch does not hold the composer, since it adds nothing to the conversation it came from. It ends when the conversation's stored messages (the messages query, not what is shown) hold the send's message id, or a branch or new conversation is in the stored list, or two readings in a row (`READINGS_TO_END_HOLD`) of the wallet's pending count whose requests were sent after the hold began (on this page) are each zero or below the highest such reading (`endsHoldAt`, `notePendingCount`; not for a branch, whose fee moves no count; an older reading neither ends it nor sets that highest, and a reading that is neither starts the count again, so one lagging node's zero does not end it), or `HOLD_LASTS_MS` (the refund timeout and `REFUND_UNLOCK_MARGIN_MS`, so it never ends while the Refund button is still locked) after the send was confirmed. Every reading counts, not only a change: the poller gives each one to `onReading` with the time its request was sent (`createStatePoller`), and `useLiveResponse` passes both to `notePendingCount`, because the answer can land before the hold exists (a save given up on after 30 s) and the count is then back where it was with nothing changing. Cancel and refund are never held. The console and the report get the error's name only, never its message (Sentry's console breadcrumb would carry it) or the prompt's text. Each of these steps runs even if another throws, and the lock is released whatever happens. The `e2e/__guards__/one-send-at-a-time` guard requires each wrapped mutation to be declared with the key, no other mutation to have it, no other source file to name a wrapped mutation, the chat to pass the flag on, each of the chat's four paid-send `onSuccess` handlers to be an `async` arrow that awaits or returns every local-store save it calls (`addMessageToConversation`, `createNewConversation`, `editUserMessage`, `regenerateAssistantResponse`, `branchConversation`) and starts nothing it does not wait for (`.then(`, `setTimeout`, `queueMicrotask`, `void`, a running `(async () => …)()`), each `onSuccess` to check `isStillActive(` after its save, the composer's call (known by its saves) in its own `onSaveFailed` to return only if its conversation is no longer open and otherwise clear with `reset()`, call `showUnsavedPrompt` with the receipt's ids and the confirmation time and `openCancelWindow(confirmedAt)`, with no other way out, and the edit call to close the edit box only while its conversation is open. It also pins the hold's wiring: the answer's actions get `heldReason={unsavedSend.heldReasonFor(message.id)}`, the edit control and the edit box `heldReason={unsavedSend.editHeldReason}`, the hold reads `storedMessages: messagesFromQuery`, and `useLiveResponse` passes every reading, with its request time, to `notePendingCount`.

**Fee token (`src/config/feeToken.ts`)** — which token pays the fees is a build setting, `VITE_FEE_TOKEN`, exactly `SENSE` or `ABLE`. A build or dev server in any mode, localnet included, stops unless it is set (`assertFeeTokenConfig` in `src/config/feeTokenConfig.ts`, called from `vite.config.ts`; the e2e harness's sync always writes it on localnet); a misspelt value stops everywhere, and the message describes the refused value by its shape only (`describeShape` in `src/lib/settingShape.ts`, shared with the store check), never the value. Only the unit tests fall back to `SENSE` when it is unset. The fallback is not safe for a deployed build: `SENSE` settings on another token mean a wrong label, no value shown and a first offer to approve the whole balance.

The setting selects a profile: symbol, name, logo, ABI, decimals, whether a market value may be shown (`showsMarketValue`, with `plannedPriceUsd` for test-chain estimates), whether the wallet panel offers send and buy (`transferable`, `purchasable`), whether its owner can pause it (`pausable`, which the fee token check asks), and the default plan limit (`fixed`, or the wallet's balance, which the plan dialog labels "your full balance", or "your balance in whole tokens" when a fraction is left out, while that offer stands: `fullBalanceLabel`). A wallet holding less than the plan's first offer of a token that is neither `purchasable` nor `transferable`, on a chain with no faucet, is pointed to SenseAI on X and the SenseAI Telegram group (`pointsToCommunity` in `src/lib/whereToGetToken.ts`; the links live only in `src/config/communityLinks.ts`, shown by `CommunityLinksNotice` in the plan dialog and, with no faucet to offer, in the insufficient-balance toast's `InsufficientBalanceNotice`). Components read `FEE_TOKEN` and never test for a particular token, so a build for the other token changes only the setting; `feeToken.test.ts` pins both profiles. No price is fetched or shown when `showsMarketValue` is false (`shouldFetchMarketPrice` in `useTokenPrice.ts`; `PlanValueEstimate.tsx` renders nothing and never mounts the price hook). The four connected-wallet buttons share `src/config/walletPanel.ts` (the `wallet-panel-shared` guard); hiding send and buy hides them for every asset in that panel, which is deliberate. The `e2e/__guards__/fee-token-literals` guard forbids a token's name (on its own, glued to letters, or joined by a dash or underscore in lower case) anywhere in `src/`, stylesheets included, outside the two fee token modules and the ABIs, comments included, and in `index.html`, `vite.config.ts` and the text files under `public/` (images and fonts are skipped by extension). It also reads the e2e suite's code (every `.ts`, `.tsx`, `.js` and `.mjs` file under `e2e/` but the guards and the unit tests: the helpers, page objects, fixtures, specs and the testnet scripts) and `playwright.config.ts`, comments left out, where a token's name, a lower-case one in a regular expression included, also fails: the suite reads the symbol and the rules from the profile (`e2e/helpers/feeToken.ts`). In `src/vite-env.d.ts` only the doc comment (one line or several) ending just above the `VITE_FEE_TOKEN` declaration, which documents the setting's two values, may name them.

**Fee token check (`src/lib/feeTokenCheck.ts`, `src/hooks/useFeeTokenCheck.ts`)** — the build setting and the escrow's stored token are not tied together by anything, so with a wallet connected the dApp reads the chain and compares, in this order, one read at a time: the code at the escrow address; the escrow's token (its getter name is spelled only in `feeTokenConfig.ts`) against `VITE_TOKEN_CONTRACT_ADDRESS`; the escrow's `evmAIAgent()` against the chain's configured agent (`CONTRACTS[chainId].agent.address`; with none configured nothing is read and the state is `unknown`); the code at the token address; the token's on-chain symbol against the profile's; `paused()`, only when the profile is `pausable`; and, for a token that is not `transferable`, `isTransferExempt` for the escrow and for the treasury the escrow holds. The order matters: a restricted-token build pointed at an ordinary token cannot be asked about listings (the read reverts), and its symbol is the answer. Code is read with `eth_getCode` from `thirdweb/rpc`, not thirdweb's bytecode helpers, which keep an answer; only `0x` (or `0x` and zeros) means no contract, and anything that is not hex is no answer. An empty answer is read once more before it counts (a lagging backend behind a load-balanced node can answer `0x` for a deployed contract): code on the second read carries on, a failed or non-hex second read is no answer, and only two empty answers in a row give `contract-not-found`. An address whose first answer has code is read once. It guards against a mistake in setting up a build or a deployment, not against a hostile build: the addresses it checks come from the same build. `blocksAction(state, action)` says what each verdict switches off. `contract-not-found` (no code at the escrow or the token), `escrow-uses-other-token`, `escrow-serves-other-agent` (a prompt would be paid for and never answered), `symbol-mismatch`, `token-paused` and `escrow-not-exempt` stop every paying action (`prompt`, which covers regenerate and a resent edit; `plan`; `branch`; `metadata`, which is rename and delete). `treasury-not-exempt` stops only `branch` and `metadata`: a prompt goes user to escrow to treasury and a restricted token allows a transfer when either end is listed, so prompts and plans still work. Cancel and refund are never switched off, though the token may itself refuse them (cancel pays its fee to the treasury; a refund leaves the escrow); a paused token refuses both, and the `token-paused` banner says so and that the payment stays with the escrow. The `treasury-not-exempt` banner says a cancellation will be refused (its fee goes from the user straight to the treasury) and that an unanswered prompt can be refunded after an hour; the `escrow-not-exempt` banner says cancelling and refunds are refused too (both pay out of the escrow). The check reaches the paying actions only through the payment gate (`usePaymentGate`, below, which also reads the prompts switch): the gate is in `useChatMutations` and, for a plan, in `src/features/usage/usePlanMutations.ts` (setting a plan asks the gate inside its mutation; revoking never asks; each receipt's `status` is read, since thirdweb resolves a reverted transaction: a reverted approval approved nothing and no limit is sent; when the approval was confirmed and the limit then fails or reverts, `LimitNotSetError` ("Limit Not Set") says the approval stands and the token approval is now the new amount (it replaced the allowance, so an earlier plan's limit still stands on the escrow but can spend only up to the new approval), that the limit can be set again and Revoke works once no prompt is pending, with the reason last (first line, scrubbed, at most 120 characters), and when thirdweb gives up waiting for the limit's receipt ("not found after … blocks") it says "Limit Not Confirmed" (it may still be set); in both the plan and balance are read again. When thirdweb gives up waiting for the approval's own receipt, it is "Approval Not Confirmed" (it may still be mined; no limit is sent; the plan and balance are read again), not "Transaction Failed". A failed set ("Transaction Failed") or revoke ("Revoke Failed") says what holds in a fixed sentence and then only the first line of the error, scrubbed and capped, never the raw message. Revoke cancels the escrow's limit (its receipt's `status` read: a reverted cancel is "Revoke Failed" and nothing more is read or sent; when thirdweb gives up waiting for the cancel's receipt it is "Revoke Not Confirmed", a warning that it may still be mined, nothing is called revoked, and the plan and balance are read again), then reads `allowance(owner, escrow)` on the fee token (`src/features/usage/escrowReads.ts`, standard signatures) and, above zero, sends `approve(escrow, 0)` as a second step ("Step 2/2"); "Access Revoked" is shown only once both are done. The limit goes first, so a declined second step leaves no limit standing. Before the second step the wallet's selected account is compared with the one the revoke started with (letter case aside); another account, or none, sends nothing more ("Account Changed": the approval was not removed because the account changed, with no retry action, since it would act for the account selected now). Then the account's `spendingLimits` on the escrow is read again, since another tab or device may have set a plan while the cancel was confirmed (one query client holds only its own plan transactions to one at a time): a limit standing again sends nothing more ("Plan Active Again": the plan revoked is cancelled, a plan is active again and its approval was left for it, Revoke removes that one too; no retry action, since the removal would be refused), and a read that fails sends nothing more ("Plan Not Checked", offering the removal, which reads the limit itself first). When that step is declined, fails or reverts ("Approval Not Removed"), its receipt does not come ("Removal Not Confirmed"), or the allowance cannot be read ("Approval Not Checked"), `ApprovalNotClearedError` says the plan is revoked and what is left, the plan and balance are read again and the dialog closes, and the notice (one id, kept until closed) offers "Remove approval", which runs `clearApprovalMutation` for the account the notice was raised for (it carries that account, and every notice the removal raises in turn carries it on): while another account is selected (letter case aside) it sends and reads nothing and replaces the notice with "Account Changed" (the approval was not removed because another account is selected than the one the notice was for; no retry action, since it would act for the account selected now). That removal reads the account's `spendingLimits` on the escrow first and sends one `approve(escrow, 0)` only when no limit stands (an expired one still stands) and an approval is left (`allowance` read next; zero sends nothing and says it is removed, a failed read sends it all the same, since an approval of zero changes nothing else), and once it is done says "Approval Removed" (it revoked no plan), and when it fails or its receipt does not come says only what is left, not that a plan was revoked; while one stands it sends nothing, takes the old notice down and says a plan is active and Revoke is the way to remove it ("Plan Is Active"), and when the read fails it sends nothing and says to try again ("Plan Not Checked", offering the removal again) (`ClearApprovalRefusedError`). Setting a plan reads `pendingEscrowCount(owner)` on the escrow before anything is built and, above zero, sends nothing ("Prompt Pending": the plan can be changed once the prompt is answered, cancelled or refunded), since the escrow refuses the limit with `HasPendingPrompts` after the approval has already replaced the old one; the dialog is disabled too, but on the count it last read, so this is what catches a prompt sent from another tab; a read that fails refuses nothing (the escrow's refusal is then a limit not set). A revoke the escrow refuses with `HasPendingPrompts` (by name or by selector) is "Prompt Pending" too: the plan still stands and can be revoked once the prompt is settled. Setting a plan takes that notice down once the plan is about to be sent (not when the gate or a pending prompt refuses it). An approval left with no plan (a half-finished revoke, a revoke from before revoking removed the approval, another device, a reload) is read from the chain by `useLeftoverApproval` (key `['usagePlan', chainId, owner, 'leftoverApproval']`, so every plan refresh reads it again; a failed read shows nothing) and told of on the onboarding screen, where no plan is shown, by `LeftoverApprovalNotice` ("Token approval left", with a "Remove approval" button described by the notice) through the same `clearApprovalMutation`, which there acts for the account selected when it is pressed: the notice is read for that account and is read again when it changes. Set, revoke and the removal are one plan transaction at a time: each is declared with `PLAN_SEND_KEY` and refuses a press while any of them is pending in the query client, from any mounted dialog or notice (`useIsPlanSendUnderWay`; the dialog and the notice's button are disabled meanwhile); where a failure shows a notice with an action, the plan and balance are read again without being waited for, so that action is not refused. Neither the revoke nor the removal asks the gate): each paying `mutationFn` in `useChatMutations` calls `refuseIfSwitchedOff(action)`, and setting a plan runs `if (paymentGate.blocks('plan')) throw new PaymentSwitchedOffError(…)`, before anything is sent and the error handler shows the banner's words (`PaymentSwitchedOffError`'s message is the title and description of what stops the action, so the rename dialog shows them too); `useChatMutations.gate.test.tsx` and `usePlanMutations.test.tsx` drive the real mutations under every state and prove nothing is encrypted, prepared or sent. The composer and the plan dialog's submit are also disabled, and so is every other control for a switched-off action, with the reason as its tooltip and accessible description; the icon buttons, the history menu items and the delete confirmation's Continue are marked with `aria-disabled`, not the native attribute or Radix's `disabled`, so they stay in the Tab and arrow-key order and show the reason on focus, and their click does nothing (`useSwitchedOffReason(action)`, worded by `switchedOffReason` in `src/lib/paymentGate.ts`, shown by `SwitchedOffButton`): regenerate and the branch menu on an answer, edit on a prompt and the save of an edit, rename and delete in the history menu (`ConversationActionsMenu`, where the switched-off reason comes before the user's own) and the rename dialog's submit. The cancel and refund buttons never ask. `PaymentsSwitchedOffBanner` (nothing to click) says what is off: it is in `MainLayout`, and because a modal dialog's backdrop hides the page's banner, the plan, rename and delete confirmation dialogs (`DeleteConversationDialog`) mount it themselves and their reasons point at the notice above (`useSwitchedOffReason(action, 'dialog')`). No answer is not a disagreement: before the first answer, or when the first read fails or returns something the contract does not declare, the state is `unknown` and nothing is stopped, with one exception: setting a plan approves the token, so the plan dialog's submit and `usePlanMutations` hold it while `useIsAwaitingFirstAnswer()` is true (the check can read this chain and has never answered; the submit is `aria-disabled` with `AWAITING_CHECK_REASON` as its description, and revoking is never held). While held, the check is asked again every `AWAITING_RECHECK_MS` (5 s) while the page is visible, and at once when the held submit is pressed (`useAskFeeTokenAgain`); a refusal or hold is titled "Not sent". Once any answer has come it is not held again, since the query keeps its last answer; where the check reads nothing (no wallet, or no contracts or agent for the chain) nothing will ever answer, so the plan is not held there. A failed read is rethrown, so the query retries it and keeps its last answer: a confirmed block stays until a read passes. The report does not carry the original error (thirdweb's batch text holds the RPC URL and the other calls in the batch, which can hold the wallet address): `src/lib/feeTokenCheckFailure.ts` sorts it into a kind (`invalid-reading`, `zero-data`, `rpc`, `node`, `no-contracts`, `other`) and keeps its first line with URLs as `<url>` (any scheme; with none, a host with a port, a path or a query, a user part before a host, and a bracketed IPv6 literal), `0x` or `0X` plus nine or more hex digits and sixteen or more bare hex digits (an underscore before them does not hide them) as `<hex>`, capped at 120 characters; a bare four-byte selector (`0x` and exactly eight) is kept, since that is how a token's error arrives from a public node, and so is a source file with its line and column; JSON-escaped slashes and a percent-encoded colon, slash or at sign are read as plain before matching; it never throws (anything it cannot read is `other` with no line). A new `FeeTokenCheckFailure` carrying only that is sent once per page load per chain and kind (tags `check: fee-token` and `failure: <kind>`, fingerprinted by kind). The same scrub (`src/lib/scrubSecrets.ts`) runs on every Sentry breadcrumb (`scrubBreadcrumb` in `src/config/sentry.ts`, as `beforeBreadcrumb`): console lines and fetch and XHR requests keep their message and string data scrubbed, nested data such as a console line's raw arguments is dropped, and a breadcrumb that cannot be read is dropped. Error and transaction events are scrubbed too (`src/config/sentryEvent.ts`, as `beforeSend` and `beforeSendTransaction`): exception values, message, log entry, transaction name, request URL and headers, and the string values of tags, extra, each context and each span's data, and each span's description; nested data, the log entry's parameters, the request body and the query string are dropped, and so are an exception's `mechanism.data`, the request's `cookies` and `env`, each span's `links`, and `http.query`, `http.fragment` and `server.address` in span data (set on every fetch span; a query string or host label can carry an RPC key). Kept as they are: stack frames, exception types, a span's own ids, and in the trace context `trace_id` (exactly 32 lower-case hex characters) and `span_id` and `parent_span_id` (exactly 16), which link a transaction to its spans and errors; any other value under those names is scrubbed. Not touched at all: the user, the fingerprint, frame variables and a breadcrumb's category (none is set to anything secret today). An event that cannot be read is dropped whole. The scrub reads at most 2048 characters of a piece of text and drops the rest, marked `…[shortened]`, so its cost is bounded. The answer is asked for again every five minutes (`FEE_TOKEN_RECHECK_MS`), since a token's owner can change the list or pause the token. The `e2e/__guards__/transaction-senders` guard (thirdweb's and viem's senders, `wallet_sendCalls`, and thirdweb's pay and transaction widgets; the wallet panel's `ConnectButton` only in the four files that share its settings) lets a transaction be sent only from `useChatMutations.tsx`, `usePlanMutations.ts` and the local faucet, and the `e2e/__guards__/payment-gate` guard pins each place the payment gate is asked (it reads code with comments stripped and matches whole statements, so a commented-out refusal or a flag with a condition added fails), that cancel, refund, revoke and the approval removal (`useClearApprovalMutation`, the helpers it sends through, the reads in `escrowReads.ts`, and `LeftoverApprovalNotice` with `useLeftoverApproval`, which it pins to the onboarding screen) never mention it, and that only `usePaymentGate` reads the check or the switch, and `feeTokenCheck.abi.test.ts` pins the reads against the synced ABIs.

**Prompts switch (`src/lib/promptsSwitch.ts`, `src/lib/promptsSwitchSource.ts`, `src/hooks/usePromptsSwitch.ts`; the gate in `src/lib/paymentGate.ts`, `src/hooks/usePaymentGate.ts`)** — the owner can close paid actions for one network and agent without a deploy, for changing the contract pair, for maintenance and for incidents (ADR-0008). The switch is the Firestore document `senseai_prompts_switch/{chainId}_{agentLowercase}` (the build's `VITE_CHAIN_ID` and `VITE_AGENT_CONTRACT_ADDRESS`; `switchDocId`), `{ closed, reason: 'pair-retired' | 'maintenance' | 'incident', updatedAt }`, which the rules let anyone `get` and nobody list or write from a client. `promptsSwitchSource.ts` holds the one `onSnapshot` (with `includeMetadataChanges`, so a server answer is told apart from a cached one) and a store that `usePromptsSwitch` reads with `useSyncExternalStore`: one listener however many components ask, closed when the last one unmounts, and a change re-renders every reader, so an open tab closes and reopens with no reload. A listener that errors is started again after `SWITCH_RETRY_MS` (30 s) while anything reads it, and a new reader does not cut that wait short. Listener trouble is reported to Sentry once per page load per kind (`src/lib/promptsSwitchReport.ts`; tags `check: prompts-switch` and `failure`): a Firestore error by its code only (`listener-<code>`, never the message), Firestore not starting (`no-firestore`), and no server answer within `SWITCH_FIRST_ANSWER_MS` (60 s) of listening while `navigator.onLine` is true (`no-server-answer`, skipped when a listener error already explains it; a blocked Firestore host looks offline to the SDK, so the error callback never fires). A report never changes the state: a reading is saved and published before its fault is reported, and a report that throws is caught. What a reading means is `parseSwitchSnapshot`: only the server's word counts; absent or `closed: false` is open; `closed: true` with a known reason is closed in that reason's words; anything else present (no `closed`, a `closed` that is not a boolean, a missing reason, a reason this build does not know) is closed in generic words and reported to Sentry once per page load per kind (`malformed` or `unknown-reason`; tags `check: prompts-switch` and `fault`), with the document's shape only (`describeSwitchDocument`, using `describeShape`), never its values; an error, an offline start or a cached answer is no answer and the last confirmed state is kept. A confirmed closure is saved in `localStorage` per document (`savedSwitchKey`) so it holds through a reload made offline, and a confirmed open clears it; storage that throws leaves the state in memory only. Before any answer with nothing saved the state is `unknown`, which stops nothing (an outage must not stop every payment). A build with no usable chain id or agent listens to nothing and is open, as the fee token check reads nothing without contracts. No text from the document is ever shown: `switchCopy` holds the words for each reason (what is closed, that cancelling, refunds and revoking still work, for `pair-retired` to reload later for the new version, and for the others that the notice is removed when prompts reopen and to reload the page if it stays; never that it goes away by itself, since a tab whose listener keeps failing never hears the reopening). The words name no position ("the other notice on this page", never "below"): they also reach toasts and dialogs. `usePaymentGate` is the only reader of `useFeeTokenCheck()`, `usePromptsSwitch()` and `readPromptsSwitchNow()`: `gateBlocks` stops every paid action while the switch is closed and otherwise equals `blocksAction`; `gateCopy` lists the banner's notices with the switch first and the fee token notice after it (beside a fee token notice the switch says the closure does not affect money back, rather than that it works, since a paused token refuses refunds); `gateNotice` is the words for a refused action and `PaymentSwitchedOffError` carries them. Cancel, refund and revoking a plan never ask. The plan's hold for the check's first answer is unchanged. Setting a plan asks the gate's current state again (`blocksNow('plan')`, which reads the switch's store at that moment through `readPromptsSwitchNow` and the latest fee token verdict) after the approval is confirmed and before the limit is built; a refusal there is a `LimitNotSetError`, so the user is told the approval stands and how to revoke it. The `e2e/__guards__/prompts-switch-source` guard keeps the collection's name in `promptsSwitchSource.ts` alone, one `onSnapshot` and no Firestore write there, the store read only through the hook, and no raw HTML in the banner or the switch modules.

**Contract errors (`buildErrorHandler` in `useChatMutations.tsx`, `src/lib/contractErrorSelector.ts`)** — an error is recognised by its name or by its selector. Both are needed: a local node writes the name into the message, while a public node returns only revert data, and thirdweb decodes that against the contract that was called, so an error raised by the token inside an escrow call arrives as a bare selector. The selector is taken from the canonical signature (name and bare parameter types); viem's `toFunctionSelector` given an error item hashes the `error` keyword and parameter names too and matches nothing. A new message needs a row in the by-selector table in `useChatMutations.errors.test.ts`. A cancellation pays its fee from the user's wallet through the plan (`cancelPrompt` checks the remaining limit and then pulls the fee with `safeTransferFrom`), so for the cancel alone the escrow's `InsufficientSpendingLimitAllowance` and the token's `ERC20InsufficientAllowance` and `ERC20InsufficientBalance` are worded as the fee not taken ("Could Not Cancel": the plan's remaining limit, the token approval or the balance is below it; nothing was cancelled; the prompt can be refunded one hour after it was sent unless it is answered first), never as raising the limit, which is switched off while a prompt is pending; other actions keep their wording. A refused transfer (`TransferNotAllowed`) is worded by action and, for a cancellation, by the check's current verdict (`refusedTransferMessage` in `src/lib/feeTokenRefusal.ts`, which `buildErrorHandler` is given the verdict for): a payment took nothing; a cancellation leaves the fee held, and the refund is promised only under `treasury-not-exempt` (a refund leaves the escrow, so under `escrow-not-exempt` it would be refused too and the message says to contact support; under `token-paused` it uses the paused wording below; under `contract-not-found` or `escrow-serves-other-agent` the message names no refund time and says to contact support; any other state offers the refund without a promise); a refund needs support. A paused token (`EnforcedPause`, the same `refusedTransferMessage` with the `paused` cause) is worded by action too, whatever the verdict: a payment took nothing; a cancellation leaves the fee held and nothing moves until the token is resumed, after which the oracle may still answer the prompt (and take the payment), or it can be cancelled, or refunded one hour after it was sent; a refund can be tried again once the token is resumed, unless the prompt has been answered by then. No time is given for the resume. The same cancellation wording is used under the `token-paused` verdict.

**Faucet (`src/hooks/useFaucetRequest.ts`, `src/lib/faucetOutcome.ts`, `src/lib/faucetService.ts`)** — both places that offer the faucet (the insufficient-balance toast from `useChatMutations`, whose `InsufficientBalanceNotice` is handed the button's label and handler, and `ManagePlanModal`) call the one `useFaucetRequest` hook. A request closes no toast but, from the insufficient-balance toast (`requestTokensFromOffer`), that toast itself by its fixed id (`FAUCET_OFFER_TOAST_ID`): a dismissal of every toast would also withdraw the update prompt, which reads a dismissal it did not cause as the user declining. It waits with `awaitFaucetReceipt`, which gives back the mined receipt or `timeout`; `faucetOutcome` maps that to `received`, `reverted`, `no-transfer` or `timeout`, and `faucetNotice` maps the outcome to what the user is told. Tokens are announced only when the receipt succeeded and holds a `Transfer` log from the configured fee token contract to the user's address (addresses compared without regard to case), and the amount shown is the one in that log, formatted with the profile's decimals: the faucet sends whatever token its own setting names, so a successful receipt alone proves nothing. A successful receipt that brought the user nothing says so plainly and is reported to Sentry once per page load (tag `check: faucet`); a reverted one says nothing was added, and a timeout says the transfer is still confirming and that the balance is not checked again for it (only a return to the tab or a reload asks again). The balance is refreshed only for `received` and `timeout`. A faucet call that throws takes its loading notice down, says the faucet failed and is logged with `console.error`. A wait for the receipt that throws replaces the sent notice with "Transfer Not Confirmed" (check your balance) and is logged the same way. The chain is read once, when the request is made. With no fee token configured for the wallet's chain the faucet is not asked: the user is told it is not available and Sentry gets a setup fault, once per page load (same tag). The `e2e/__guards__/faucet-single-handler` guard keeps it that way: the faucet is asked and its receipt awaited only in the hook, the result is worded only in `faucetOutcome.ts`, and every file that offers the faucet calls `useFaucetRequest()`.

Contracts are configured in `src/config/contracts.ts` keyed by `chainId`, populated from Vite env vars (`VITE_CHAIN_ID`, `VITE_TOKEN_CONTRACT_ADDRESS`, `VITE_AGENT_CONTRACT_ADDRESS`, `VITE_ESCROW_CONTRACT_ADDRESS`). ABIs live in `src/lib/abi/`.

- `useChatMutations` — all blockchain write operations (prompt, regenerate, branch, metadata, cancel, refund)
- `useLiveResponse` — real-time on-chain state poller (no log watching) and query invalidation

A refund the contract still refuses as too early is worded as the hour not yet having passed on the network, though it may have on the device's clock, and the refund opening once it has; no time is promised, since a device clock that runs ahead makes the wait as long as it is ahead

### ABI Sync Process

ABIs in `src/lib/abi/` are not hand-maintained — they are synced from compiled contract artifacts:

```bash
# 1. Compile contracts in their repos (required first)
cd ../able-contracts && bun run compile
cd ../sense-contracts && bun run compile
cd ../tokenized-ai-agent && bun run compile

# 2. Sync ABIs into this repo
bun run sync-contracts
```

Run this whenever contracts change. Stale ABIs produce silent parse failures when reading on-chain events.

### Critical ABI Contract

`PromptSubmitted` event param order (enforced by contract tests in `tokenized-ai-agent`):

```
(address indexed user, uint256 indexed conversationId, uint256 indexed promptMessageId,
 uint256 answerMessageId, bytes encryptedPayload, bytes roflEncryptedKey)
```

`answerMessageId` is at **param index 3** (0-based, non-indexed). `useChatMutations.tsx` reads it at this index from the receipt log. If this ever changes, both the subgraph and dApp must be updated in lockstep.

### Protocol Constants

| Constant                  | Value              | Where used                      |
| ------------------------- | ------------------ | ------------------------------- |
| `CANCELLATION_TIMEOUT_MS` | 3 000 ms (3 s)     | Cancel button disable countdown |
| `REFUND_TIMEOUT_MS`       | 3 600 000 ms (1 h) | Refund eligibility display      |

These are hardcoded in `EVMAIAgentEscrow`. Do not guess at them — verify against the contract.

### VITE_ORACLE_PUBLIC_KEY

`VITE_ORACLE_PUBLIC_KEY` must match the public key of the active ROFL TEE oracle instance. If this key is stale or missing, `createEncryptedPayloads()` either fails silently or produces ciphertext the oracle cannot decrypt — prompts are submitted on-chain but never answered. Validate this key is present and current whenever the oracle is redeployed.
